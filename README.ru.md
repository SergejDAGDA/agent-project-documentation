# Project Documentation

Универсальный Agent Skill для превращения исходного репозитория в структурированную, поддерживаемую и пригодную для повторного использования базу знаний о проекте.

Навык формирует два уровня документации:

1. Презентационный уровень для человека, который впервые открывает проект.
2. Внутренний уровень для разработчика или AI-агента, которому нужно подробно понять функциональность, архитектуру, реализацию и возможности повторного использования.

Навык также умеет документировать сами Agent Skills и plugin-репозитории.

## Зачем это нужно

README недостаточно для сохранения знаний о проекте.

Исходный код показывает реализацию, но обычно не сохраняет в удобном виде функциональный контракт, ожидаемое поведение, ограничения, границы повторного использования и общую карту возможностей.

`project-documentation` извлекает эти знания из репозитория и отдельно описывает поведение продукта и текущую техническую реализацию.

Это позволяет использовать документацию для:

- презентации проекта на GitHub
- онбординга
- сопровождения
- аудита документации
- подготовки релиза
- внутреннего сравнения исходного плана с фактической реализацией
- проверки проекта перед продолжением разработки
- поиска случайных привязок к старым проектам, примерам и пользовательскому контексту
- работы AI-агентов
- передачи проекта другому разработчику
- повторного использования решений в новых проектах
- документирования Agent Skills и plugins

## Модель документации

```text
Repository
|
|-- Presentation layer
|   `-- README.md и применимые публичные инструкции
|
|-- Internal knowledge
|   |-- индекс возможностей
|   |-- функциональные контракты
|   |-- архитектура
|   |-- описание реализации
|   |-- разработка и эксплуатация
|   |-- заметки для повторного использования
|   `-- при необходимости история plan vs implementation
|
|-- Local diagnostics
|   `-- .project-documentation/
|
`-- Optional agent routing
    `-- указатели из AGENTS.md или CLAUDE.md
```

Структура адаптивная. Навык не создает пустые документы про API, базу данных, deployment и другие части, которых в проекте нет.

## Основные возможности

- анализ структуры репозитория
- определение типа проекта
- обнаружение значимой функциональности
- презентационная документация
- подробная внутренняя документация
- извлечение функциональных контрактов
- привязка поведения к текущей реализации
- извлечение переиспользуемых решений
- статусы доказательности verified, partial и unverified
- аудит документации
- точечное обновление документации после изменений кода
- проверка документации перед релизом
- специальный профиль для Agent Skills и plugins
- внутренний reconcile исходного плана и фактической реализации
- continuation audit для поиска следов отпавших и незавершенных решений
- contamination audit для поиска случайных привязок к прошлым проектам, примерам, пользователям и окружениям
- безопасное редактирование credential-like значений в диагностике
- детерминированные вспомогательные скрипты для инвентаризации, проверки Markdown и диагностических сигналов

## Режимы

```text
init
  Первичное документирование существующего проекта

audit
  Аудит документации и ее соответствия репозиторию

update
  Обновление только затронутой изменениями документации

presentation
  Работа с публичным и GitHub-представлением проекта

internal
  Подробная функциональная и техническая документация

release
  Проверка документации перед релизом

extract
  Извлечение знаний для повторного использования в другом проекте

skill-docs
  Документирование Agent Skill или plugin-репозитория

reconcile
  Сравнение принятого плана проекта с текущей реализацией

continuation
  Поиск следов старых, отпавших или незавершенных решений

contamination
  Поиск случайной привязки к предыдущим проектам, пользователям, окружениям и примерам
```

## Документирование skills

Если репозиторий содержит Agent Skills, навык анализирует применимые `SKILL.md` и связанные ресурсы.

Он может документировать:

- условия срабатывания
- workflow и режимы
- references
- scripts
- assets
- agent metadata
- plugin manifests
- MCP-зависимости
- платформенную упаковку
- границы переносимости
- правила сопровождения

Ядро skill остается единым. Платформенная упаковка для совместимых сред располагается вокруг него и не требует второй копии основных инструкций.

## Структура репозитория

```text
skills/

  plugin.json
```

## Вспомогательные скрипты

Инвентаризация репозитория:

```bash
python skills/project-documentation/scripts/repository_inventory.py --root . --format markdown
```

Проверка структуры Markdown и Agent Skills:

```bash
python skills/project-documentation/scripts/documentation_audit.py --root .
```

Сбор консервативных сигналов для continuation и contamination audit:

```bash
python skills/project-documentation/scripts/repository_diagnostics.py --root . --format markdown
```

Известные названия старых проектов, клиентов или источников можно передавать повторяющимся аргументом `--marker`. Диагностические результаты по умолчанию должны оставаться в `.project-documentation/`, который исключен из Git.

Скрипты помогают агенту, но не заменяют анализ исходного кода, language-specific static analysis, secret scanning и security review.

## Принципы

### Сначала доказательства

Важные утверждения документации должны опираться на актуальное содержимое репозитория.

### Сначала поведение, потом реализация

Переиспользуемая функциональность сначала описывается как функциональный контракт, а затем как конкретная текущая реализация.

### Адаптивная структура

Состав документации определяется проектом, а не жестким шаблоном.

### Без лишнего переписывания

Имеющая смысл авторская документация должна сохраняться. Режим update меняет только знания, которые действительно затронуты изменениями проекта.

### Повторное использование без слепого копирования

Reuse notes описывают переносимое поведение, границы, предположения, зависимости и ограничения.

## Статус
