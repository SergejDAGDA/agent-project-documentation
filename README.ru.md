# Project Documentation

[English version](README.md)

Универсальный Agent Skill для превращения исходного репозитория в структурированную, поддерживаемую и пригодную для повторного использования базу знаний о проекте.

Имя репозитория: `agent-project-documentation`

Имя установленного Agent Skill: `project-documentation`

Вызывать как: `$project-documentation`

Навык формирует два уровня документации:

1. Презентационный уровень для человека, который впервые открывает проект.
2. Внутренний уровень для разработчика или AI-агента, которому нужно подробно понять функциональность, архитектуру, реализацию и возможности повторного использования.

Навык также умеет документировать сами Agent Skills и plugin-репозитории.

## Зачем это нужно

README недостаточно для сохранения знаний о проекте.

Исходный код показывает реализацию, но обычно не сохраняет в удобном виде функциональный контракт, ожидаемое поведение, ограничения, границы повторного использования и общую карту возможностей.

`project-documentation` извлекает эти знания из репозитория и отдельно описывает поведение продукта и текущую техническую реализацию.

Это позволяет использовать документацию для:

- презентации проекта на GitHub
- онбординга
- сопровождения
- аудита документации
- подготовки релиза
- внутреннего сравнения исходного плана с фактической реализацией
- проверки проекта перед продолжением разработки
- поиска случайных привязок к старым проектам, примерам и пользовательскому контексту
- работы AI-агентов
- передачи проекта другому разработчику
- повторного использования решений в новых проектах
- документирования Agent Skills и plugins

## Модель документации

```text
Repository
|
|-- Presentation layer
|   `-- README.md и применимые публичные инструкции
|
|-- Internal knowledge
|   |-- индекс возможностей
|   |-- функциональные контракты
|   |-- архитектура
|   |-- описание реализации
|   |-- разработка и эксплуатация
|   |-- заметки для повторного использования
|   `-- при необходимости история plan vs implementation
|
|-- Local diagnostics
|   `-- .project-documentation/
|
`-- Optional agent routing
    `-- указатели из AGENTS.md или CLAUDE.md
```

Структура адаптивная. Навык не создает пустые документы про API, базу данных, deployment и другие части, которых в проекте нет.

## Основные возможности

- анализ структуры репозитория
- определение типа проекта
- обнаружение значимой функциональности
- презентационная документация
- подробная внутренняя документация
- извлечение функциональных контрактов
- привязка поведения к текущей реализации
- извлечение переиспользуемых решений
- статусы доказательности verified, partial и unverified
- аудит документации
- точечное обновление документации после изменений кода
- проверка документации перед релизом
- специальный профиль для Agent Skills и plugins
- внутренний reconcile исходного плана и фактической реализации
- continuation audit для поиска следов отпавших и незавершенных решений
- contamination audit для поиска случайных привязок к прошлым проектам, примерам, пользователям и окружениям
- безопасное редактирование credential-like значений в диагностике
- детерминированные вспомогательные скрипты для инвентаризации, проверки Markdown и диагностических сигналов

## Безопасное поведение по умолчанию

Если запрос не называет режим и не просит явно менять файлы, навык начинает с анализа репозитория и read-only audit.

Обнаружение устаревшей документации само по себе не означает разрешение на `update`.

Project-memory и coordination artifacts распознаются по назначению, а не только по каталогу. Сильные признаки: имена вроде `*HANDOFF*.md` и `*CHECKPOINT*.md`, точные файлы `STATUS.md`, `DECISIONS.md`, `SESSION_LOG.md`, основной заголовок, явно обозначающий handoff/checkpoint/status/log, а также явно выделенные project-memory каталоги.

Такие файлы можно читать как evidence, когда этого требуют локальные инструкции проекта или когда они действительно нужны для понимания текущего контекста, но обычное сопровождение документации не должно автоматически их переписывать. Конфликты выводятся в `Out-of-scope coordination findings`, если пользователь отдельно не включил их сопровождение в задачу.

## Режимы

```text
init
  Первичное документирование существующего проекта

audit
  Аудит документации и ее соответствия репозиторию

update
  Обновление только затронутой изменениями документации

presentation
  Работа с публичным и GitHub-представлением проекта

internal
  Подробная функциональная и техническая документация

release
  Проверка документации перед релизом

extract
  Извлечение знаний для повторного использования в другом проекте

skill-docs
  Документирование Agent Skill или plugin-репозитория

reconcile
  Сравнение принятого плана проекта с текущей реализацией

continuation
  Поиск следов старых, отпавших или незавершенных решений

contamination
  Поиск случайной привязки к предыдущим проектам, пользователям, окружениям и примерам
```

## Примеры запросов

### Первый общий прогон

Используй этот вариант, если нужно сначала понять состояние существующего репозитория и не предполагается автоматическое редактирование.

```text
Используй $project-documentation для текущего репозитория.
Начни с анализа структуры и read-only audit.
Скажи, какие режимы документации здесь применимы и что требует внимания.
Не меняй файлы без моего явного запроса на update.
```

### Обновление документации после изменений кода

```text
Используй $project-documentation в режиме update.
Проверь текущий Git diff и изменения реализации.
Обнови только действительно затронутую поддерживаемую документацию.
Считай handoff, status, decisions, session-log, checkpoint и project-memory файлы отдельно сопровождаемыми coordination artifacts, если я явно не включил их сопровождение в задачу.
Найденные out-of-scope coordination findings выведи отдельно.
```

### Полная внутренняя документация

```text
Используй $project-documentation в режиме internal.
Задокументируй текущий репозиторий как поддерживаемую базу знаний о проекте.
Отделяй функциональные контракты от деталей реализации и добавляй reuse notes для значимых возможностей.
```

### Презентационный GitHub README

```text
Используй $project-documentation в режиме presentation.
Проверь и улучши GitHub-facing документацию так, чтобы новый читатель быстро понял, что это за проект, что он умеет, как начать работу и где лежит подробная документация.
Не превращай README во внутреннее описание архитектуры.
```

### Сравнение исходного плана с реализацией

```text
Используй $project-documentation в режиме reconcile.
Сравни принятые требования, MVP-документы и зафиксированные решения с текущей реализацией.
Классифицируй расхождения и не придумывай причины там, где они документально не установлены.
Результат оставь во внутренней документации, а не в публичном README.
```

### Проверка перед продолжением разработки

```text
Используй $project-documentation в режиме continuation.
Проверь репозиторий на abandoned, superseded, stale, orphaned, compatibility и incomplete-migration residue.
Любую находку считай кандидатом на ручную проверку, а не разрешением удалять код.
```

### Проверка на наследие старых проектов

```text
Используй $project-documentation в режиме contamination.
Поищи случайные привязки к старым проектам, example data, пользовательским путям, клиентским значениям и особенностям конкретного окружения.
Не копируй credential-like или приватные значения в отчет.
```

### Извлечение переиспользуемой функциональности

```text
Используй $project-documentation в режиме extract.
Найди возможности, которые можно переиспользовать в другом проекте.
Для каждой полезной возможности отдельно опиши функциональный контракт, текущую реализацию, зависимости, предположения, ограничения и reuse notes.
```

### Документирование другого Agent Skill

```text
Используй $project-documentation в режиме skill-docs.
Подготовь документацию этого Agent Skill репозитория для пользователей и сопровождающих.
Опиши trigger contract, workflows, references, scripts, packaging, portability boundaries и maintenance contract.
```

## Документирование skills

Если репозиторий содержит Agent Skills, навык анализирует применимые `SKILL.md` и связанные ресурсы.

Он может документировать:

- условия срабатывания
- workflow и режимы
- references
- scripts
- assets
- agent metadata
- plugin manifests
- MCP-зависимости
- платформенную упаковку
- границы переносимости
- правила сопровождения

Ядро skill остается единым. Платформенная упаковка для совместимых сред располагается вокруг него и не требует второй копии основных инструкций.

## Структура репозитория

```text
skills/
  project-documentation/
    SKILL.md
    agents/
      openai.yaml
    references/
      documentation-model.md
      feature-documentation.md
      quality-gates.md

      contamination-audit.md

.claude-plugin/

```

## Вспомогательные скрипты

Инвентаризация репозитория, когда она нужна для discovery:

```bash
python skills/project-documentation/scripts/repository_inventory.py --root . --format markdown
```

Проверка структуры поддерживаемых документационных Markdown-файлов и Agent Skills:

```bash
python skills/project-documentation/scripts/documentation_audit.py --root .
```

Обычный audit по умолчанию исключает Markdown, используемый как данные, а также отдельно сопровождаемые coordination artifacts вроде handoff и project-memory файлов. Проверка вообще всех Markdown-файлов включается только при сознательно выбранной широкой области:

```bash
python skills/project-documentation/scripts/documentation_audit.py --root . --all-markdown
```

Сбор консервативных residue/contamination сигналов запускается только для continuation, contamination, явно запрошенной широкой диагностики или конкретного расследования, которому действительно нужны такие эвристические сигналы:

```bash
python skills/project-documentation/scripts/repository_diagnostics.py --root . --format markdown
```

Известные названия старых проектов, клиентов или источников можно передавать повторяющимся аргументом `--marker`. Диагностические результаты по умолчанию должны оставаться в `.project-documentation/`, который исключен из Git.

`repository_diagnostics.py` не является рутинным quality gate для обычных `init`, `audit`, `update`, `presentation` или `release`.

Скрипты помогают агенту, но не заменяют анализ исходного кода, language-specific static analysis, secret scanning и security review.

## Принципы

### Сначала доказательства

Важные утверждения документации должны опираться на актуальное содержимое репозитория.

### Сначала поведение, потом реализация

Переиспользуемая функциональность сначала описывается как функциональный контракт, а затем как конкретная текущая реализация.

### Адаптивная структура

Состав документации определяется проектом, а не жестким шаблоном.

### Без лишнего переписывания

Имеющая смысл авторская документация должна сохраняться. Режим update меняет только знания, которые действительно затронуты изменениями проекта.

### Coordination остается отдельно сопровождаемой областью

Handoff, checkpoint, project status, decisions, session log и project-memory файлы могут использоваться как evidence, но не входят автоматически в обычный documentation update.

### Повторное использование без слепого копирования

Reuse notes описывают переносимое поведение, границы, предположения, зависимости и ограничения.

## Статус

Версия 0.2.2 уточняет семантическое распознавание coordination artifacts, исключает их из обычного Markdown audit по умолчанию и запускает repository diagnostics только в режимах, которым действительно нужны эвристические residue или contamination сигналы.
